# Harbor low-level design

## Order service

The Java service is the authority for catalog pricing, customer ownership, operator access, idempotency, status transitions, and cancellation. The current implementation is under `order-service/src/main/java/io/orderflow`.

### Placement and transitions

1. Require an authenticated customer and a bounded `Idempotency-Key`.
2. Validate at least one item, unique SKUs, and integer quantities from 1 through 99.
3. Resolve each SKU against the active catalog; never trust client-supplied price or customer identity.
4. Compute line and order totals using integer minor units and overflow-checked arithmetic. Canonicalize sorted SKU/quantity pairs and hash the request.
5. Insert a `PENDING` order. A repeated key with the same request returns the original order; reuse with a different request returns `409 IDEMPOTENCY_PAYLOAD_MISMATCH`.
6. The legal forward path is `PENDING → PROCESSING → SHIPPED → DELIVERED`. Cancellation is allowed only from `PENDING`. Updates increment `version`, append to `history`, and use compare-and-set on the expected status and version.

Production orders are eligible immediately. The five-minute Go worker poll moves each due order on the next poll. Local Java uses a 30-second eligibility delay and a 15-second scheduler interval to leave time to try cancellation.

### Persistence adapters

`OrderRepository` is the storage boundary. `InMemoryOrderRepository` is used outside the `prod` profile; it owns its records and secondary indexes under a read/write lock. Newest-first pages seek through sorted indexes using `(createdAtEpochMillis, orderId)`. The due queue uses numeric epoch milliseconds so whole-second and fractional timestamps remain correctly ordered. Expected list lookup cost is O(log n + page size) for the indexed filters.

`JdbcOrderRepository` is selected by the `prod` profile. The `orders` table stores searchable order/status/customer/deadline/version/idempotency columns plus the serialized order view. Unique constraints enforce order ID and `(customer_id, idempotency_key)`. SQL indexes support customer/status pages and due-order scans. Status changes update only rows matching the expected status and version. The production H2 URL points to `/data/harbor-orders`; Compose mounts `/data` to a named volume. H2 is suitable here for a single-node evaluation deployment, not for shared multi-replica storage.

### HTTP API

Customer and operator APIs require `Authorization: Bearer`. Customers can access only their own orders. Operators can inspect orders and move status forward.

| Method and path | Behavior |
|---|---|
| `POST /api/auth/login` | Verifies configured credentials and returns a short-lived token |
| `GET /api/catalog` | Returns active catalog entries |
| `POST /api/orders` | Places an idempotent multi-item customer order |
| `GET /api/orders/{orderId}` | Gets an owned order or an operator-visible order |
| `GET /api/orders?status=&customerId=&limit=&cursor=` | Lists customer-scoped or operator-filtered pages |
| `POST /api/orders/{orderId}/cancel` | Cancels only a pending customer order |
| `PATCH /api/orders/{orderId}/status` | Applies one legal operator transition |
| `GET /internal/orders/due?limit=50` | Lists due pending order IDs; internal token required |
| `POST /internal/orders/{orderId}/promote` | Promotes a due order to `PROCESSING`; internal token required |

List page sizes are bounded to 100. The opaque cursor contains the last timestamp and order ID. Both repository adapters use the same descending keyset ordering. API responses omit internal idempotency fields and the numeric timestamp index.

### Security and configuration

Production users are loaded from a read-only JSON file with Argon2id password hashes generated by `PasswordHashTool`. Startup rejects missing users, seeded accounts, weak JWT/internal/database secrets, malformed password hashes, and malformed user records. The Go worker validates that production does not use the local token. Local demo accounts and their password are for development only.

## Status worker

The Go worker polls Java's internal due-order endpoint. It promotes IDs in bounded batches with up to four concurrent requests, drains additional due batches, and relies on Java's compare-and-set to handle races. Transport and server errors trigger a short retry; shutdown cancellation is passed through the in-flight HTTP requests.

In secure Compose, `INTERVAL=5m`. In demo Compose it is `15s`. For standalone local runs, either use Java's embedded scheduler or set `ORDERFLOW_EMBEDDED_PROMOTE=false` and run the Go worker; do not enable both for ordinary development.

## Intake service

`CatalogIndex` tokenizes active catalog fields once. `FixtureModel` selects bounded catalog candidates from a user's sentence. `ground` rejects inactive or unknown SKUs and invalid quantities, then replaces model-supplied names and prices with the catalog values. The intake service produces a draft only; Java validates the final order independently.

## Web app

Next.js App Router screens use route handlers to proxy API calls. The browser stores the short-lived token only in an HTTP-only session cookie. Route handlers attach correlation IDs, validate order identifiers, restrict forwarded query parameters, and send requests with `no-store`. The cart is in `sessionStorage` and is cleared only after a successful place response.
